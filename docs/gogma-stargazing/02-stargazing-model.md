# 观星原理与记录模型

本文依据社区资料 [S3][S4] 与 GogmaSeedFinder 的 RNG 实现 [S11]；操作计数是本项目的展示模型，底层算法见[种子恢复与未来预测](05-seed-prediction.md)。

## 1. “随机”与“可复现”不矛盾

游戏向玩家提供随机结果，但在同一存档基线、相同操作条件下，社区观察到重抽序列可重复。玩家先试抽记录，然后不保存回到该基线，就能再次走到已经看过的位置。[S3][S4]

这里的“表”是**结果序列的行为模型**，不证明游戏内部存着一张实体表。也没有证据表明所有玩家共享相同种子或相同第 N 抽结果。

## 2. 结果表与推进位置是两件事

### 2.1 结果表按武器种类与属性区分

S3 举例：火长枪、龙长枪、龙狩猎笛各有不同的结果序列；攻击激化龙长枪和会心激化龙长枪可以看到相同的对应重抽结果。S4 也限定为“同属性、相同武器”。

因此推荐的初步结果表标识是：

```text
存档基线 + 规则版本 + 抽取轨道 + 武器种类 + 属性/异常类型 + 操作模式
```

保留加成重抽还必须记录五条从左到右的类别布局。S11 的 Keep 公式只依赖类别布局，不依赖旧档位；不同布局不能合并。接受/拒绝操作仍记录用于核对游戏进度，公式一致性与实机验证范围见专题。

不要只按“火属性”合并火太刀与火大剑；也不要因为激化方向不影响已观测结果就丢弃激化字段，它仍决定性能与材料费用。

### 2.2 同一轨道共享推进

根据 S3、S4，在一把武器上抽一次，同一轨道内其他巨戟武器的表也向前一格。换武器不是从另一张表的第 1 格重新开始。

假设技能轨道中，自基线已实际抽取 `c` 次，下一次结果位于第 `c+1` 格：

```text
result = observedTable[weaponType, attribute][c + 1]
c = c + 1
```

这是人工记录模式的查表表达。恢复 `baseSeed` 和对应绝对 counter 后，也可按 S11 算法生成尚未观测的结果；同一轨道仍共享推进位置。

### 2.3 两个独立轨道

| 轨道 | 记录内容 | 社区描述的推进操作 |
| --- | --- | --- |
| 技能 S | 系列技能 + 组合技能 | 技能重置；机械武器升级成巨戟武器 |
| 加成 R | 五条类别与档位 | 完全重抽加成；保留类别重抽档位 |

S3 明确两条轨道独立。工具至少要有 `skillCursor`、`reinforcementCursor` 两个位置。普通机械武器生产、任务、炼金等其他行为的影响本次没有完整证据，不应自动假定能用它们垫刀。

S11 将底层状态明确为一个共同 `baseSeed` 和独立的 `skillCounter`、`gogmaCounter`。界面相对游标 0 不等于游戏绝对 counter 为 0。上游已实测“复原不推进技能”，反向独立性仍以存档字段与公式为依据，未完成独立实机对照。

首次巨戟升级消耗一次技能抽取，与所耗零件数量无关。[S3] “造完再开始试抽”通常最容易避免错位。

## 3. 编号约定

- 基线：`c = 0`，表示还没进行本轮的任何一次抽取。
- 第 `n` 抽：完成第 `n` 次操作后展示的候选结果，采用 **1 起始编号**。
- 已推进：`c`，只统计当前实际执行分支已经发生的抽取。
- 距目标还要抽：`n - c`，**包含目标那一次**。
- 目标前垫刀次数：`n - c - 1`。
- `n <= c`：该目标位置已被消费，不能靠换一把武器重新领取。

例如目标在第 15 抽、当前已推进 6 次：先垫 8 次，第 9 次在目标武器上抽取。不是垫 9 次再抽。

## 4. 为什么多武器可以节省材料

以下仅为演示编号的虚构数据，不是任何玩家的真实技能表：

| 目标 | 从同一基线试抽得到的目标位置 |
| --- | ---: |
| A：火太刀的一组目标技能 | 4 |
| B：冰大锤的一组目标技能 | 9 |
| C：雷斩斧的一组目标技能 | 15 |

从基线开始依次消费 4、5、6 次操作，分别在第 4、9、15 格给对应武器兑现，可在总计 15 次内获得三把目标。

如果按错误顺序先冲到第 15 格，就已经错过第 4 和第 9 格。把每把武器的初始距离 `4+9+15=28` 当成同一执行分支的总费用，也是不正确的。

### 同格冲突

如果 A 与 B 都只在第 4 格有目标，一次操作只能作用于一把武器。兑现 A 后，B 的第 4 格已经过去。回档拿 B 会失去尚未进入该存档的 A，不能同时保留两条分支成果。

因此应保留每把武器的多个候选位置，并允许优先级取舍或继续试抽。简单“取最远位置”只适用于**目标不冲突、轨道一致、观测兼容且没有额外推进操作**的路径。

## 5. 垫刀改变的是费用，不是目标结果

S3、S4 建议准备不同激化方向的备用巨戟武器。目标武器若为攻击激化，而攻击零件紧张，可在已准备好的属性激化武器上用属性零件做前面的无目标技能抽取，再在目标格切回攻击激化武器。

材料匹配按“激化方向”而不是武器属性：

```text
一次技能抽取消耗 = 匹配方向零件 3 个，或非匹配方向零件 6 个
```

例如第 15 格才有目标：14 次匹配方向垫刀需 42 个对应零件，最后一次需 3 个目标方向零件。总次数仍是 15；如果本来就全用匹配材料，总零件数也仍是 45。节省发生在避免非匹配的 6 个支付、均衡稀缺方向库存，或顺路拿到其他武器目标时。

备用武器应在建立基线前造好；临时升级备用巨戟武器本身会推进技能表，不能忽略。[S3]

## 6. 预算模型

来自 S5 的社区费用预设：

```text
技能费用 = 9,000z × 技能操作次数
加成费用 = 10,000z × 加成操作次数
全用七色金石的加成材料 = 20 × 加成操作次数
```

零件费用必须按执行计划逐步汇总到攻击/会心/属性三个库存，不能仅显示一个“总零件数”。初始制备成本单列。未实测的混合支付不自动安排。

还应区分：

1. **试抽所需临时库存**：一次连续试抽能走多远；回档后可恢复到基线库存。
2. **正式兑现永久消耗**：按选定路径真正保存下来的材料消耗。
3. **未来预算**：从当前已兑现位置开始计算，不能把历史消耗再加一次。

## 7. 建议记录结构

这是未来实现建议，不代表本次已实现：

| 对象 | 最少字段 |
| --- | --- |
| 基线 | `baselineId`、游戏版本、平台、角色标识、建立时间、库存快照 |
| RNG 状态 | `baseSeed`、`gogmaCounter`、`skillCounter`（未知可空）、门控条件、算法版本、候选搜索范围与验证状态 |
| 预测 | 基线 ID、绝对 counter、相对编号、模式、武器种类/属性、Keep 类别布局、生成结果、算法版本；与实测记录分开 |
| 武器实例 | `weaponId`、种类、属性/异常、三个生产加成、激化方向、当前五条加成、当前技能 |
| 观测 | 基线 ID、轨道、模式、抽取编号、武器 ID、输入加成、完整候选结果、接受/拒绝、截图备注 |
| 目标 | 武器 ID、要求/可接受替代、候选观测编号、优先级 |
| 执行日志 | 步骤 ID、轨道、前后位置、武器、材料实际消耗、结果是否吻合、游戏是否已保存 |

试抽和正式兑现各自维护状态：试抽计数增加不等于游戏主存档进度增加。回到基线会撤回游戏操作，但不能删除外部记录的未来结果。

## 8. 已有预测能力与边界

- S11 已实现种子恢复及 Reset、Keep、技能未来列表生成，不再需要逐格试抽全部目标。
- 搜索唯一性依赖输入、门控条件和搜索范围；有限范围的唯一候选不等于任意范围全局唯一。
- Keep 依赖有序类别布局；技能与 Keep 有公式测试，独立实机验证仍待补充。
- 尚未证明跨角色、平台、版本的序列等价，也未确认全部失败/取消/拒绝操作的游标行为。

结果应区分“算法预测”“玩家实测”“同条件复现”；未知 RNG 状态时保留人工记录能力。详细算法与输入要求见[专题](05-seed-prediction.md)。

# 纯 JavaScript 种子搜索计算评估

日期：2026-10-26。上游固定提交 `65789e9aa17e434a7f5d74d18ab1f9e1365920eb`。

## 结论

**纯 JS 搜索有计算可行性，可以作为不依赖 WASM/Worker 的方案；但手机首次全范围识别的体验仍取决于 counter 范围。**

本次已经在桌面 Chromium 的受限 CSP 页面上完成一亿种子、单位置的完整搜索：36.276 秒，正确且唯一返回 `(86315169, 480)`。搜索在主线程按约 8ms 分块，不是一次阻塞 36 秒。

不能由此推导小黑盒手机上也需要 36 秒。真实 WebView 的 JIT、机型、功耗、温度、前后台行为尚未测量。相比技术选型，未知 counter 范围过宽仍是更大的产品问题。

## 实现与正确性

实验代码：[experiments/gogma-js](../../experiments/gogma-js/README.md)。未接入应用入口。

- 按上游实现 100 轮初始化、32 位无符号右移与溢出，使用 Number/位运算，不在热循环中使用 BigInt。
- 观测一次性编译为取模区间；错误种子在首个不匹配槽位淘汰。
- 保留 GF(2) 快速跳转，使用 64 KiB 字节查表加速每个种子的跳转应用。
- 每种子初始化一次，随后遍历 counter 区间。热循环使用四个标量，避免每次 RNG 转移都写 TypedArray。
- 主线程块间使用 `setTimeout` 让出任务队列；仅 `await Promise.resolve()` 不足以让渲染和输入任务执行。

129 组验证通过：

1. 三组上游六抽实机 fixture（斩斧、弓、重弩）：初始化状态、预测结果、邻域搜索一致。
2. 14 武器 × 3 属性（含无属性）× 3 种子（含 0 与 u32 上界）的 126 组差分：30 行预测和小区间候选集合与上游 WASM 一致。
3. 性能测试所有区间均与 WASM 搜索结果一致；一万行 JS 预测逐项与 WASM 一致。

这验证了实验移植与参考实现一致，不扩大上游游戏版本及实机验证范围。本次只评估已启用 counter gate 的 Reset 搜索。

## Bun/JSC：纯计算对照

环境：Apple M4、Bun 1.4.0；单线程，三次计时取中位数。JS 使用查表优化，WASM 为上游现成二进制，二者并非完全相同的底层优化策略。

| counter 数量 | 实测种子数 | JS 中位耗时 | WASM 中位耗时 | JS/WASM |
| --- | --- | --- | --- | --- |
| 1 | 100 万 | 0.213 秒 | 0.254 秒 | 0.84 |
| 11 | 100 万 | 0.433 秒 | 0.402 秒 | 1.08 |
| 101 | 100 万 | 2.415 秒 | 1.665 秒 | 1.45 |
| 1001 | 10 万 | 2.243 秒 | 1.442 秒 | 1.56 |
| 2001 | 10 万 | 4.432 秒 | 2.860 秒 | 1.55 |

已知种子、位置，JS 生成一万行 Reset 结果约 32.6ms（含本次 JS 预测函数的跳转准备，不含 UI 渲染）。这条预测路径仍使用方便验证的数组权重计算，没有做极致优化。

**JS 不必然比 WASM 慢一个数量级**。本原型说明精确整数运算、预编译约束、跳转及热点数据布局，比仅凭语言推断性能更可靠。

## Chromium：主线程实际等待时间

环境：同机 Apple M4，OpenCode 2.1.4 内嵌 Electron 44.9.1 / Chromium 152.0.7977.167。以下最终测量期间没有同时运行 CLI 性能基准。

独立页面 CSP：

```text
default-src 'none'; script-src 'self'; worker-src 'none';
connect-src 'none'; style-src 'unsafe-inline'
```

无 WASM、无 Worker、无 eval、无计算网络请求；不包含小黑盒 Runtime。这验证普通 Chromium 下的相关 CSP 障碍可以由纯 JS 避开，不等同于通过小黑盒真机验收。

| counter 数量 | 实测种子数 | 纯计算累计 | 含让出主线程的总耗时 | 一亿种子等待时间估算 |
| --- | --- | --- | --- | --- |
| 1 | 100 万 | 0.251 秒 | 0.398 秒 | 另有完整实测：36.276 秒 |
| 11 | 100 万 | 0.526 秒 | 0.849 秒 | 约 85 秒 |
| 101 | 100 万 | 3.210 秒 | 5.041 秒 | 约 8.4 分钟 |
| 1001 | 10 万 | 3.006 秒 | 4.713 秒 | 约 78.6 分钟 |
| 2001 | 10 万 | 6.046 秒 | 9.480 秒 | 约 158 分钟 |

后四行的一亿种子时间是按样本线性外推，不是完整搜索实测或手机性能承诺。窄范围围绕 counter 480；1001/2001 个位置分别为 `0..1000`、`0..2000`。种子样本从 86,300,000 开始。

完整一亿种子试验：`0..99,999,999`，固定 counter 480，重弩六抽观测：

- 总耗时 36.276 秒；累计纯计算 23.180 秒。
- 唯一返回 `(86315169, 480)`。
- 单块 P95 8.2ms、最长 12.9ms。
- 16ms 心跳定时器最大额外延迟约 8.3ms。这是事件循环响应指标，不是完整输入延迟或帧率测量。

分块为响应性付出了调度成本，但能让 UI、进度和取消处理获得运行机会。不能直接把 CLI 的连续循环耗时当成产品等待时间。当前每块目标 8ms，批量按实际吞吐调整、上限 50,000；游戏手机可进一步降低目标并测量代价。

初期 TypedArray 热循环的浏览器成绩显著更差，随后改为标量后改善；初期还存在并行基准干扰，因此旧数字不作为最终基准。原型说明跨 JS 引擎单独测量很重要。

## 产品取舍

建议首版采用以下计算边界，待真机测试后确定具体默认值：

1. **已知种子导入、续接与预测：优先提供。** 计算规模小，无需重新枚举一亿种子。
2. **已知或窄范围 counter 的纯 JS 搜索：可实现。** 用短校准阶段估算吞吐，显示预计等待时间，并支持进度与取消。
3. **几十到上百个位置：作为显式长任务。** 桌面已可能达到分钟级，移动端需根据本机实测预算决定搜索范围。
4. **上千个未知位置：不作为默认首次识别流程。** 分块只改善响应，不会减少总计算量；增加样本也不会消除遍历位置范围的成本。
5. **保存已完成种子区间，而不是只保存 UI 百分比。** 分块计算使暂停/恢复可以后续实现；本原型只有取消，尚未实现持久化恢复。

纯 JS 无法解决“玩家完全不知道历史抽取位置”这个信息问题。需求设计应明确如何取得位置估计，或提供已有状态导入；不要把工具中的相对第 0 抽当成游戏 counter=0。
